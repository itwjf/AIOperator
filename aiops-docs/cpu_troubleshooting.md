# CPU 性能问题排查指南

## CPU 使用率过高的常见原因

在生产环境中，CPU 使用率突然飙升是最常见的告警类型之一。主要原因包括：

1. **死循环或无限递归** — 代码 bug 导致进程无法跳出循环
2. **GC 频繁触发** — Java/Go 程序的内存分配过快，导致垃圾回收占用大量 CPU
3. **线程竞争** — 过多的线程争抢锁资源，上下文切换消耗 CPU
4. **大量请求涌入** — 没有做好限流，瞬时流量打满 CPU

## 排查步骤

### 1. 定位高 CPU 进程

首先使用 `top` 命令查看系统整体情况：

```bash
top -bn1 | head -20
```

找到 CPU 使用率最高的进程 PID 后，进一步查看该进程的线程：

```bash
top -H -p <PID>
```

### 2. 分析线程堆栈

拿到高 CPU 的线程 ID 后，用 `jstack`（Java 应用）或 `perf`（C/C++ 应用）抓取堆栈：

```bash
# Java 应用
jstack <PID> > jstack.log

# 将线程 ID 转换为十六进制（jstack 里的 tid 是十六进制）
printf "%x\n" <TID>

# 在 jstack 输出中搜索该线程
grep -A 20 "nid=0x<HEX_TID>" jstack.log
```

### 3. 检查 GC 日志

如果是 Java 应用，GC 问题通常表现为 CPU 高但业务吞吐低：

```bash
# 查看 GC 频率和耗时
jstat -gcutil <PID> 1000
```

关注 YGC（Young GC）和 FGC（Full GC）的频次。如果 FGC 持续增长，说明存在内存泄漏或堆内存配置不足。

### 4. 检查系统调用

用 `strace` 追踪进程的系统调用，找出频繁的无效操作：

```bash
strace -c -p <PID> -T
```

## 常见案例

### 案例一：正则表达式灾难性回溯

某次排查发现一个 Java 服务的 CPU 始终 100%。最终定位到一个用户输入校验的正则表达式存在灾难性回溯问题。修复方案：重写正则，避免嵌套量词。

### 案例二：Redis 连接池耗尽

业务线程在等待 Redis 连接时自旋等待，导致 CPU 空转。修复方案：引入连接池超时机制，等待超过 1 秒时抛出异常而非自旋。

## 预防措施

- 代码审查时关注循环和正则表达式
- 配置 JVM GC 日志和 CPU 告警阈值
- 对关键接口做好限流和降级
- 定期压测，发现性能瓶颈
